# Full Qwen MoE: Adreno dense + Hexagon routed experts

The first full-model Hexagon expert run completed with exit 0 on S25 Ultra
(SM-S938W / SM8750), Android 16, native Termux. It generated 32 tokens using
20,160 QNN graph calls and 12,102 Vulkan dense dispatches. No CPU fallback
handled routed expert computation. Source matches commit `9d28a9fd`.

This is the same complete 40-layer Huihui Qwen3.6-35B-A3B text model and
converted container as the [Adreno baseline](qwen36-s25-adreno-2026-10-09.md).
All 45 file sizes and SHA-256 values were checked again immediately before
loading. The test keeps Adreno dense weights, CPU routing/attention state,
eight cached experts per layer, four CPU threads, and a 1,024-token context
limit. It replaces CPU routed-expert kernels with a dynamic FP16 QNN SwiGLU
graph. It is not an all-NPU dense-chain implementation.

## Measured comparison

| Measurement | Adreno dense + CPU experts | Adreno dense + Hexagon experts |
| --- | ---: | ---: |
| Decode step, 31 steps | 2,082.1 ms/token | 2,659.4 ms/token |
| Decode throughput | **0.4803 tokens/s** | **0.3760 tokens/s** |
| Prompt + 32 output tokens | 128.4 s | 171.8 s |
| Overall rate including prompt | 0.25 tokens/s | 0.19 tokens/s |
| Time to first token, excluding load | 63.88 s | 89.38 s |
| Resident weight load | 16.2 s | 17.2 s |
| Reported peak RSS | 2.46 GB | 2.45 GB |
| Cache hit rate, whole run | 27.7% | 28.0% |
| Expert fetch, decode | 1,163.59 ms/token | 1,137.22 ms/token |
| Expert compute/staging, decode | 731.84 ms/token | 1,333.57 ms/token |

The initial Hexagon path delivered **21.7% lower decode throughput** in these
single runs. Its expert timer includes CPU INT4-to-FP16 expansion, registered
DDR writes, QNN execution, and FP16 output conversion. It does not isolate NPU
arithmetic. Fetch includes cache lookup and weight preparation, not just UFS.
Dense-stage timing was nearly unchanged. Serial staging/execution is an obvious
optimization candidate; this measurement does not isolate how much of the
extra time each operation caused.

Precision differs: the baseline CPU expert kernel defaults to INT8 activations;
the QNN graph uses FP16 IO/computation. Both consume the same signed INT4
weights and float32 group scales. Output tokens differ, so routing and storage
accesses can also differ. These results do not establish an intrinsic CPU/NPU
hardware ratio or equal-quality throughput.

## Numerical and device checks

The first routed input vector in every layer was checked against the CPU
FP32-activation expert kernel, using identical INT4 values and float32 scales.
All 320 selected-expert comparisons passed the preselected cosine >= 0.999
and relative L2 <= 0.05 gates. Minimum cosine was 0.999642427; maximum relative
L2 was 0.026767528. Nonfinite FP16 inputs, weights or outputs fail the run.
This samples real activations but is not perplexity or full-model equivalence
qualification. Audit CPU computation is included in prefill/TTFT, not decode.

Before the run Android thermal status was 0 and skin temperature 34.2 C.
Near the end of decoding it reached status 1 (light throttling), with a sampled
skin temperature of 38.4 C; after completion it was 38.2 C. The GPU baseline
remained at status 0. The phone stayed unplugged and had 70% battery afterward.
Available system memory at inference preflight was 5,812 MiB, with existing
Android zram in use. RSS excludes some GPU/system allocations. Neither run is
a sustained, cold-cache or statistically repeated benchmark.

Independent device conversion testing compared 262,144 planar values with
Python-generated IEEE FP16 reference bytes, covering all signed codes,
float32 scales, subnormal/rounding cases and invalid/overflow rejection.
Profile rejection tests and the normal CPU build, dense-batch and context
regressions also passed. QNN cleanup completed without reported error.

with the exact prompt and Vulkan settings from the baseline. Add the

there. PILOT remains 0. The two registered 6 MiB expert buffers alternate
serially; there is no reader/compute overlap, native INT4 HMX claim, or direct
TCM allocation in this adapter. QNN owns internal placement. The static dense
chain and asynchronous full-model integration remain future work.
